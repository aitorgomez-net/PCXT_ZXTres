Hardware

The ZXTRES boards

The ZXTRES, ZXTRES+ and ZXTRES++ by Antonio Villena are the same board with three sizes of Artix-7. The core uses the board's SDRAM for the PC's memory, ROMs and video memory, its SRAM for the 350-line scan converter, the VGA connector, the audio jack and I2S, the two PS/2 ports, the two DB9 joystick ports and the microSD card through the DeMiSTify controller.

Port

What differs from the MiSTer core

The machine RTL is the MiSTer RTL: zxtres/rtl/pcxt_zxtres_guest.sv is generated from PCXT.sv by zxtres/scripts/make_guest.py, which copies the machine blocks as they are and adds the board glue. Only the logic around the machine is specific to the board.

The A35T builds are limited by LUTs, not by block RAM: the full core needs about 25,000 LUTs and the XC7A35T has 20,800. 05

Optimisation

Making the core fit the XC7A35T

Two changes to the shared machine RTL made the whole core smaller, on every board and on MiSTer alike; build switches then leave out what a single-machine build does not need.

vram_fetch snoop

The video fetch engine computed a 24-bit offset and compare for every entry and every write word. It now takes one difference per entry and an AND-OR per word. Out of context on the XC7A35T: depth 3×1 word 1,592 → 671 LUTs, 4×1 2,109 → 880, 4×2 2,872 → 1,216. A lockstep bench against the previous version shows no difference.

Microcode in block RAM

Vivado had turned the 4K×32 MCL86 microcode ROM into LUTs. Its read is already registered, so a block RAM gives the same one-clock latency. The narrow operand-select copy stays a LUT ROM, as it starts the critical path.

ENABLE_RTC, ENABLE_COM2

New build switches leave out the RTC/CMOS device and the second serial port: the ports are not decoded, the device raises no interrupt and synthesis trims it. Both default to 1, so the MiSTer profiles are unchanged.

Builds without EMS

The EMS map reset used reset || !`ENABLE_EMS as an asynchronous reset, a constant one when EMS is left out, which Vivado refuses (Synth 8-91). The asynchronous reset is now the reset alone, and a build without EMS clears the map synchronously.

With these changes the A100T full core went from 29.8k LUTs and 30 block RAM tiles (17 November 2026) to 25.0k LUTs and 34 tiles (22 November). Each A35T profile then leaves out C/MS, COM2, MIDI and, except the PCjr, the RTC, plus the machines and cards it does not carry.

The OSD of a single-machine build

The configuration string of the OSD is the same in every build, but the firmware is built with the build's profile (build_firmware.sh <profile> writes its VERILOG_MACRO lines into build_features.h). Its menu_mask() uses the build's fixed machine and card instead of the status bits and hides the entries of hardware the build lacks: Machine, Video card, Audio 220h, SB IRQ and UMB C400. The status bits keep one layout, so PCXT.CFG is read the same way by every build. The core itself ignores the machine and card bits in a single-machine build. All builds use the EGA layout of the MiSTer status word (LAYOUT_EGA=1), the one the ZXTres OSD feeds.

From source

Building

The build needs Vivado 2025.2, Python 3, and nasm, gcc and make for the controller firmware (from WSL if the host is Windows). The DeMiSTify and mist-modules submodules must be checked out. Run the scripts from the repository root, from Git Bash on Windows or from Linux:

git submodule update --init --recursive
zxtres/scripts/build_firmware.sh                 # EightThirtyTwo toolchain and firmware (full core)
zxtres/scripts/build_pcxt.sh                     # ZXTRES+ (A100T), full core
zxtres/scripts/build_pcxt.sh A200T               # ZXTRES++ (A200T), full core
PCXT_PROFILE=zx3_a35t_pcxt_cgahgc zxtres/scripts/build_pcxt.sh A35T
PCXT_PROFILE=zx3_a35t_pcxt_ega    zxtres/scripts/build_pcxt.sh A35T
PCXT_PROFILE=zx3_a35t_tandy1000   zxtres/scripts/build_pcxt.sh A35T
PCXT_PROFILE=zx3_a35t_pcjr        zxtres/scripts/build_pcxt.sh A35T
BoardProfileOutput
A100Tmister_pcxt_fullbuild/zxtres-pcxt/vivado-pcxt/PCXT.ZX3
A200Tmister_pcxt_fullbuild/zxtres-pcxt/vivado-pcxt-a200t/PCXT.ZX3
A35Tzx3_a35t_* (default zx3_a35t_pcxt_cgahgc)build/zxtres-pcxt/vivado-pcxt-a35t-<profile>/PCXT.ZX3

The .bit file and the timing and utilization reports are written next to the .ZX3. build_pcxt.sh first checks that the committed guest is not stale (make_guest.py --check) and rebuilds the firmware with the build's profile. build_pcxt.sh A100T project (or A200T) writes zxtres/vivado/create_project_A100T.tcl, which creates the Vivado project from inside Vivado on any host; the A35T builds have no project mode.

The MiSTer Quartus project (PCXT.qsf, config.tcl, the mister_* profiles) is still in the repository, as the source of the machine; it is not used for the ZXTres builds.

07

Checks

Verification

  • zxtres/scripts/make_guest.py --check: the committed guest matches PCXT.sv, every OSD file entry finds its own extensions, and the configuration string stays within the 2047 bytes user_io serves.
  • Unit tests in zxtres/sim (WSL or Linux, Verilator and Icarus): the IDE and floppy stores against the machine's own devices, the line doubler, the scan converter, the video information page, the OSD, the keyboard relay with the machine's KFPS2KB, the ROM loading queue, the status bits 64–127, the serial mouse and the ICAP warm boot of the return to the Spectrum core.
  • Whole-board simulation, zxtres/sim/run_bios_sim.sh: the real firmware on the GHDL-converted controller loads the ROMs from a simulated card and the machine runs the BIOS POST. +OSD_TOUR walks the OSD pages with the keyboard and render_osd_tour.sh draws them; PCXT_PROFILE selects the build.
  • Each RTL directory of the machine has a TESTBENCH/ folder of focused benches, shared with the MiSTer core.
  • A Vivado build with no critical warnings and positive WNS and WHS.

The detailed state of the port, the decisions behind it and what remains are in zxtres/SPEC.md.
